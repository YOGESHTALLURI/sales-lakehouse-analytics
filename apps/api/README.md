# API

Express + TypeScript service. It owns two clearly separated responsibilities:

- **Operational endpoints** read and write PostgreSQL.
- **Analytics endpoints** read the DuckDB warehouse, never PostgreSQL.

The HTTP contract lives in [../../docs/api/openapi.yaml](../../docs/api/openapi.yaml).

## Migrations

```bash
docker compose exec api npm run migrate      # inside the stack
npm run migrate --workspace @sales-lakehouse/api   # from the host
```

SQL lives in [../../data/postgres/migrations](../../data/postgres/migrations),
named `NNNN_snake_case.sql`. The runner is a few dozen lines of `pg` rather than
a framework, so the schema stays plain SQL an evaluator can read and there is no
tool version to keep in step with the database. It still guarantees what matters:

- **Numeric ordering**, so `0010_` cannot sort ahead of `0009_`.
- **Exactly once**, tracked in a `schema_migrations` table you can inspect with psql.
- **One transaction per file**, so a failure leaves the database on the last
  complete migration instead of half-way through one. Files therefore must not
  contain their own `BEGIN`/`COMMIT` — a test enforces this.
- **Checksums**, so editing a migration that has already run is refused. Silently
  allowing it would let the file and the live schema disagree for good, and every
  later environment would build a different database from the same repository.

## Commands

Run from the repository root:

```bash
npm install                              # installs the workspace
npm run typecheck --workspace @sales-lakehouse/api
npm test --workspace @sales-lakehouse/api
npm run dev --workspace @sales-lakehouse/api
```

`npm run dev` needs `POSTGRES_DB`, `POSTGRES_USER` and `POSTGRES_PASSWORD` in the
environment; everything else falls back to the defaults documented in
`.env.example`. Under Compose those values come from `.env` automatically.

## Seeding

```bash
docker compose exec api npm run seed          # inside the stack
npm run seed --workspace @sales-lakehouse/api # from the host
```

Generates 500 customers, 100 products and 10,000 orders across 12 months, then
**replaces** the contents of `customers`, `products`, `orders` and `order_items`
in a single transaction. `pipeline_runs` is untouched — that is the platform's
audit history, not seed data.

All of it is generated by this repository; nothing is downloaded. The inputs are
`SEED_*` in `.env` plus two committed files:

| File | Holds |
|---|---|
| [`vocabulary.json`](../../data/postgres/seeds/vocabulary.json) | Names, the controlled city/state list, product nouns and price bands |
| [`generation-profile.json`](../../data/postgres/seeds/generation-profile.json) | Category demand, seasonality, weekday rhythm, basket sizes, status mix |

### Why not Faker

The plan suggested Faker as a vocabulary source. The vocabulary is committed
instead, because seeding Faker only fixes *that library's* stream — upgrading it
would silently change every generated row and quietly break the reproducibility
requirement. With the vocabulary in-repo and a `mulberry32` PRNG in
[`random.ts`](src/seed/random.ts), the dataset depends on nothing outside this
repository.

Reproducibility is verified, not assumed: a test asserts a fixed SHA-256 of the
whole dataset — primary keys included, since UUIDs come from the seeded stream
rather than from PostgreSQL. The same checksum has been observed on a Windows
host and inside the Linux container.

### Why the data has a shape

Uniform random data makes every chart look like noise and hides whether the
aggregation works at all. So the generator models:

- **Log-uniform prices, biased low.** Retail prices span two orders of
  magnitude; a linear draw over a category's band makes flagship items as common
  as everyday ones and pushes average order value to implausible levels.
- **Seasonality and weekday rhythm** — a festive-season peak roughly 1.5× the
  February trough, and busier weekends.
- **Uneven category demand** — the leading category takes ~36% of revenue, the
  smallest under 2%.
- **A loyal minority** placing over half the orders, so top-customer analysis
  has something to find.
- **Sale prices that diverge from catalogue prices** on ~35% of lines, which is
  what makes the warehouse's use of `unit_price_at_sale` observable rather than
  theoretical.
- **Retired products** that keep their sales history but never appear on new
  orders.

Tests assert each of these properties, so a future change that flattens the data
fails rather than quietly producing a boring dashboard.

### Validation before loading

[`validate.ts`](src/seed/validate.ts) checks the dataset against every schema
constraint — uniqueness, referential integrity, money scale, one line per
product per order, status values, window bounds — and prints a report. The
database would reject most violations anyway, but a failed `INSERT` partway
through 21,000 rows names one bad row with no context. Nothing is truncated
until the whole dataset has passed.

## Design notes

- **Config is parsed once, at startup.** `loadConfig` validates the environment
  with Zod and throws before the server listens. A service that boots with a
  missing password and fails on the first request is harder to diagnose.
- **`loadConfig` takes the environment as an argument** rather than reading
  `process.env` internally, so tests supply fixtures without mutating globals.
- **Dependency probes are injected into `createApp`.** Every `/health` outcome —
  ready, warehouse-missing, database-down — is covered by tests that need no
  running infrastructure.
- **A missing warehouse is not a failure.** A fresh stack has no DuckDB file
  until the first pipeline run, so `/health` reports it and still returns 200.
  Only PostgreSQL is required for readiness.
- **Error detail never carries credentials.** pg attaches the failing client —
  and therefore its password — to some errors, so only the driver code and
  message are surfaced, any embedded connection URI is redacted, and the result
  is length-capped. Tests assert a planted password never reaches a response.
- **A PostgreSQL restart must not kill the API.** pg re-emits a dead idle client
  as an `'error'` event on the pool, and Node terminates the process on an
  unhandled `'error'` event. `createPostgresPool` attaches a listener, so an
  outage leaves the service up reporting `degraded`, and recovery is automatic.
  Verified live: stopping PostgreSQL yields `503`, restarting it yields `200`,
  with uptime unbroken.
- **The container exec's tsx directly, not `npm run dev`.** A supervisor process
  at PID 1 survives a crashed server, leaving the container `Up (unhealthy)`
  forever so Docker's restart policy never fires; it also swallows SIGTERM.
  Exec'ing tsx makes a fatal error exit the container and lets
  `docker compose stop` shut down gracefully in about a second.
