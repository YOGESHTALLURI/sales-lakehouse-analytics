# Contributing

This repository is built one cohesive boundary at a time, each on its own
branch, merged only once it is tested and verified.

## Branching

- `main` holds integrated, verified history only. Never implement on `main`.
- Every cohesive flow gets a short-lived branch cut from the latest `main` —
  for example `feat/oltp-schema`, `feat/warehouse-etl`, `fix/order-validation`.
- One boundary per branch. Do not mix frontend, API and ETL changes without a
  genuine integration reason.
- Corrective work after review goes on a narrowly named follow-up branch
  (`fix/order-validation`), never as a direct commit to `main`.
- Finish one branch — tested, committed, pushed, merged — before starting the
  branch that depends on it.

## Commits

- Conventional Commits, imperative mood: `feat:`, `fix:`, `chore:`, `docs:`,
  `test:`, `refactor:`, `ci:`.
- One logical change per commit. No "misc fixes", no commit that touches three
  unrelated boundaries.
- Commit tests alongside the code they protect. Never backfill every test in
  one final commit.
- Commit only after its verification step passes.

## Verification before every commit

Run whatever applies to the change:

```bash
docker compose config                             # Compose contract still valid
npm run lint && npm run typecheck && npm test     # API / web changes
python -m pytest                                  # ETL changes
```

Then inspect what you are about to record:

```bash
git status
git diff --cached
```

## Never commit

- `.env` or any real credential, token or key
- database volumes, MinIO objects, generated Parquet runs
- the generated DuckDB warehouse file
- `node_modules/`, build output, coverage reports

`.gitignore` covers these, but read the staged diff anyway — a `git add -A`
after a pipeline run is the usual way generated data slips in.

## Working cadence

1. Take the next smallest unchecked item on the branch.
2. Implement only that item and its directly related tests and docs.
3. Run the relevant verification.
4. Inspect `git status` and `git diff`.
5. Make one descriptive Conventional Commit.
6. Push the branch to `origin`.
7. Open a pull request into `main`, record the commit hash and the acceptance
   criteria met, and merge only after checks pass.

One push per completed vertical slice. Do not create artificial micro-commits
for single files, and do not group unrelated features together.

## Prohibited history operations

Never force-push, rewrite published history, amend a pushed commit, or squash
the project into one generated commit. The history is part of the deliverable
and must reflect the real development order.

## Architecture invariants

These are not negotiable; a change that breaks one is a bug:

- PostgreSQL is OLTP only.
- MinIO holds immutable raw Parquet. New runs create new prefixes; existing
  objects are never edited.
- DuckDB is the analytical warehouse.
- Analytics endpoints query DuckDB, never PostgreSQL.
- All business data is generated by this repository, never downloaded.
- Docker Compose stays reproducible from a clean clone.
